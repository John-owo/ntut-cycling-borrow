# 借還車系統操作與發布

本次新增完整的編號車預約流程，沿用 GitHub Pages、Supabase 與本機 Node/SQLite。舊排隊紀錄與歷史管理功能保留，與新流程共同受社車總量限制。

## 正式啟用前的實車盤點

1. 先核對原系統的社車總數、期初借出及尚未歸還紀錄。舊借用沒有可靠車號時，不猜測它對應哪一台車。
2. 011 已按提供的車名建立 1–8 號，全部先標為待盤點；1–7 號顯示來源原圖，8 號照片待補。幹部逐車編輯、填寫盤點原因後才能標為「可借」，另建立實際配件編號。只有已實際核對、目前在庫且安全可借的車能啟用；維修及已借出但尚未釐清者不得標成可借。舊總數目前為 7，需核對第 8 台及既有借出後再調整，照片不代表車已在庫。
3. 填寫真實社辦位置、取車指引及社團確認的借用規範。尚未設定時系統會拒絕預約。
4. 核驗社員姓名、學號、聯絡資料及資格期限，發出個人私人憑證。用私人管道交給本人，勿貼進公開群組或 Git。前端產生 256-bit 隨機憑證，後端僅儲存 SHA-256 雜湊。
5. 每位幹部使用原有個人登入；已啟用雙重驗證者仍須完成驗證。資格期限需涵蓋預約結束時間；停權或過期仍可查閱及歸還自己的借用。

可用編號車與舊借出合計不得超過總車數。已編入新流程的可用車，須從預約流程交車；若仍要從舊排隊交車，幹部必須先盤點並調整相應編號車狀態。這避免無車號的舊操作重複借出已預約車輛。歷史紀錄不會被自動轉換或取消。

## 社員流程

日曆查看各車及配件的預約與使用狀態 → 輸入本人憑證 → 選擇起訖時間與一台車／配件 → 預約成功 → 依指引取車。

取車時間限預約開始至結束之間。取車時上傳左側、右側、傳動及損傷細節共四項原始照片，確認車架、輪胎、煞車、變速及配件，填寫既有車況，閱讀規範後輸入本人姓名並手寫簽署。全部完成才記錄實際取車時間、進入「使用中」。照片不能證明實際人在現場，系統仍仰賴本人誠實檢查。

歸還由本人紀錄開啟，同樣拍四項照片並完成車況及配件檢查。正常歸還立即結案；任何異常或未完整的檢查會進入「待檢查」，並在幹部後台建立持續保留的通知。幹部查看前後照片、車況、簽署及操作紀錄後，以原因註記完成處理，決定恢復可借或轉維修。

逾期使用中的車即使超過原時段仍阻擋預約，直到歸還；日曆不會把它當成空車。已預約不等於已取車。取消僅限尚未取車；使用中不能透過取消跳過還車檢查。沒有自動取消或自行延長借期。

## 照片、簽署與權限

照片以原始二進位存入私有資料表，綁定借用、社員關係、車號、拍攝階段及項目，附上伺服器時間、大小及 SHA-256。原檔不壓縮、不覆蓋、不刪除；重新上傳會新增歷史。支援 JPEG／PNG／WebP，每張上限 8 MiB，每階段最多 12 張；手機預設開啟相機／圖片選擇器。HEIC 需由裝置另存成支援格式；不自動改寫來源。

原圖只能經本人憑證或幹部驗證後逐張讀取，沒有公開照片網址。日曆不含姓名、學號、聯絡資訊、簽署或照片。手寫簽署與姓名、當時規範全文、規範版本及伺服器時間一併固定保存。這是系統的同意與簽署紀錄，未整合外部身分認證或憑證簽章服務。

異常通知為站內幹部通知；本版未串接電子郵件、LINE 或推播。原圖占用 Supabase 資料庫容量與流量，請持續檢查免費方案用量，系統不會自動升級付費方案或清除照片。完整備份包含個資及原圖，僅幹部可匯出，請保存在受控位置。資料保留期限仍待社團決定。

照片應用總預算為 192 MiB，幹部可查看已用與預留量。每筆新預約須先保留四張取車與四張還車原圖的最大空間（64 MiB）；實際上傳較小檔案會釋放差額。必要還車照片的預留額度不會被其他新預約或重複照片占用。歷史原圖持續計入用量；接近滿額時拒絕新增預約／額外照片，不能靠刪除歷史繞過。空資料庫最多先接受三筆完整最大額度的預約；這是保守容量限制，並非車隊只有三台。仍須監控整個資料庫、流量及供應商額度；長期大量營運應另實作私有物件儲存與受控備份／保留政策。

## 發布順序與回復原則

1. 隔離測試通過，確認 GitHub 目標 `John-owo/ntut-cycling-borrow` 及 Supabase 專案 `isrndpzcifrvbftlauzz`。
2. 在同一正式專案只套用一次 009／010／011，不重跑 001–008。建議執行 `node scripts/lifecycle-release.mjs <新的.sql路徑>` 產生完整交易；它鎖定舊資料、在交易內比對更新前後雜湊、拒絕重跑已安裝的新流程。保留舊表與設定，僅建立已確認車名的待盤點目錄，不預填真實社員、可借狀態或位置。
3. 唯讀檢查 RPC、RLS、grants、舊紀錄數與設定。不可用真實社員或借用資料作寫入測試。
4. 提交、推送、PR 檢查通過後循正常合併與 Pages 發布；部署使用 allowlist 打包，不直接發布整個 public 目錄。
5. 正式日曆與匿名隔離讀回後，由幹部完成上述盤點與真人驗收。SQLite／PGlite 的測試不代表真人、正式 Auth 或跨連線 PostgreSQL 並發驗收。

若前端需要回復，以 Git 正常 revert／PR 回復；保留新增資料表、原始照片與簽署，禁止刪表作為回復手段。回復舊版之前須先處理進行中的新流程借用，避免前端無法歸還。
